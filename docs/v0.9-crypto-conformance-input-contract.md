# v0.9 Crypto Conformance Input Contract (4.4.4)

This document defines the input/output contract for the 4.4.4 crypto conformance validators.
The goal is deterministic, cross-language verification of the v0.9 draft's normative crypto
behavior (derived from v0.8.1 but with clarified labels, salt semantics, and nonce/AAD rules)
without requiring any one implementation to be the "oracle".

## Scope

- Handshake conformance (slice 1): transcript binding + hybrid secret derivation.
- Follow-on slices: DR/message AEAD + nonce/AAD derivation, media AEAD + nonce/AAD derivation,
  group sender-key signatures, EARE signature/PoP verification.

## Encoding Rules

- Binary values use standard Base64 (`A-Z a-z 0-9 + /`) with padding (`=`) unless otherwise
  stated.
- Integer encodings used in KDF/IV contexts MUST be deterministic:
  - `U8(x)` = 1-byte unsigned.
  - `U32BE(x)` = 4-byte unsigned big-endian.
  - `U64BE(x)` = 8-byte unsigned big-endian.
- "Concatenation" means byte concatenation of decoded byte strings and encoded integers.

## Canonical CBOR + Hashing

- `canonicalCBOR(x)` follows RFC 8949 canonical rules (map keys sorted by shortest encoding
  then lexicographic).
- `SHA256(x)` is SHA-256 over raw bytes.
- Conformance outputs MUST be reported as digests; do not emit raw derived keys.

## HKDF and Labels (v0.9 Draft)

- HKDF is HKDF-SHA256 (RFC 5869 Extract+Expand).
- Parameter order is: `HKDF(input_key_material, salt, info, L)`.
- HKDF `info` labels are ASCII bytes and MUST match exactly.
- HKDF `salt` semantics are normative:
  - default `salt = 0^HashLen` (32 bytes of 0x00 for SHA-256)
  - `salt = ""` (zero-length) is distinct and MUST NOT be substituted.

Label registry (see `spec/e2ee-protocol-specification-v0.9.md`):

- `FW-Handshake-Root`
- `FW-DR-Root`
- `FW-DR-CKS`
- `FW-DR-CKR`
- `FW-Message`
- `FW-Chain`
- `FW-StreamKey`
- `FW-MediaEpochKey`
- `FW-FrameKey`
- `FW-CP-MAC`

## Files

Two tiers are supported:

1. Shared/public vectors (checked in):
   - `tests/common/handshake/crypto_conformance_test_vectors.json`
   - `spec/crypto_conformance_test_vectors.schema.json`
2. Local secret bundle (not checked in):
   - `tests/local/handshake/crypto_conformance_secrets.json`
   - `spec/crypto_conformance_secrets.schema.json`

If the local secret bundle is missing, validators MUST still run the transcript-only checks.

## Handshake Conformance

Handshake conformance splits into two levels:

- L0 (public-only): transcript binding.
- L1 (requires local secrets): hybrid secret derivation + derived-key digests.

### L0 Inputs (public vectors)

Each case provides the canonical CBOR bytes of the raw public transcript object:

- `handshake_transcript_raw_cbor_b64`

The transcript covers (at minimum):

- `client_x25519_pub` (bstr)
- `server_x25519_pub` (bstr)
- `kyber_public_key` (bstr; v0.9: ML-KEM-1024 public key bytes)
- `kyber_ciphertext` (bstr; v0.9: ML-KEM-1024 ciphertext bytes)
- `params.crypto_suite_id` and `params.handshake_auth`

### L0 Required Computations

- `transcript_sha256 = SHA256(handshake_transcript_raw_cbor_bytes)`
- `session_id = transcript_sha256`

### L0 Expected Outputs

Public vectors include:

- `expected.session_id_b64`

### L1 Inputs (local secret bundle)

To recompute the hybrid secret, validators also load test-only private key material by
`case_id` from `tests/local/handshake/crypto_conformance_secrets.json`:

- `client_x25519_private_key_b64`
- `client_kyber_private_key_b64` (v0.9: ML-KEM-1024 private key bytes)

### L1 Required Computations (v0.9 Draft)

Derived intermediates:

- `x25519_shared = X25519(client_x25519_priv, server_x25519_pub)`
- `kem_shared = ML-KEM-1024.Decapsulate(client_kyber_priv, server_kyber_ciphertext)`

Derived secret:

- `handshake_secret = HKDF(
    input_key_material = x25519_shared || kem_shared,
    salt = 0^HashLen,
    info = "FW-Handshake-Root",
    L = 32
  )`

Key confirmation (normative; conformance MAY check a digest of the confirmation):

- `key_confirmation = HMAC-SHA256(handshake_secret, transcript_sha256)`

Control-plane MAC key (normative):

- `sp_mac_key = HKDF(input_key_material=handshake_secret, salt=0^HashLen, info="FW-CP-MAC", L=32)`

### L1 Expected Outputs

Validators MUST emit digests (Base64 of raw digest bytes) and compare them to the public
vector's `expected.*` fields when present:

- `x25519_shared_sha256_b64`
- `kem_shared_sha256_b64`
- `handshake_secret_sha256_b64`

Recommended additional digests:

- `key_confirmation_sha256_b64` (hash the 32-byte HMAC output)
- `sp_mac_key_sha256_b64`

## Strict Conformance (No Backwards Compatibility)

v0.9 conformance is strict:

- Legacy HKDF labels (for example, any `FoxWhisper-*` label strings) MUST be treated as malformed / non-conformant.
- Legacy/alternate fixture encodings (Base64url, unpadded Base64) MUST be rejected.
- Validators MUST fail cases where derived values only match under legacy labels/salt conventions.
